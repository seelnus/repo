# 生产版本发布、本地备份与快速回滚设计

**日期**：2026-08-28  
**状态**：方案已确认，待实施脚本  
**适用范围**：正式服务器 `/www/wwwroot/survey-app`  
**核心目标**：每次生产发布前生成可验证的本地完整恢复点；数据库迁移或新版本异常时能够快速恢复升级前状态。

## 1. 项目现状

根据项目 README，正式环境为阿里云 ECS 单机部署：

- 宝塔面板和 Nginx 提供 HTTPS 入口。
- Docker Compose 运行前端、后端、MySQL 8.0 和 MinIO。
- MySQL 数据库名为 `survey_app`，数据保存在 Docker 命名卷。
- 当前上传接口把附件保存到后端 `/app/uploads`，该目录由独立 Docker 卷持久化。
- MinIO 使用独立 Docker 卷；即使当前没有正式承载附件，也必须纳入备份。
- 服务器通过 Git 拉取代码并重新构建容器。
- 后端启动时自动执行 `prisma migrate deploy`，数据库迁移是前向执行，没有自动反向迁移。
- 当前 README 只有裸 `git pull` 和 `docker compose up -d --build` 发布命令，没有备份门禁、恢复验证、滚动保留和标准回滚流程。

当前架构下，容器重新创建通常不会丢数据，但以下操作具有高风险：

- `docker compose down -v`。
- 删除或重建 MySQL、uploads、MinIO 命名卷。
- 改变 Compose 项目名或部署目录后误挂载到新空卷。
- 未备份就启动包含新 Prisma 迁移的后端。
- 只回滚 Git 代码，但数据库已经执行了不兼容的新迁移。
- 只备份数据库，遗漏问卷附件或未来的 MinIO 对象。

## 2. 目标与边界

### 2.1 目标

1. 每次生产发布都自动创建发布前完整恢复点。
2. 备份覆盖数据库、上传文件、MinIO、环境配置、Compose 配置和代码版本。
3. 备份必须通过校验和临时数据库恢复测试，不能只判断“命令执行成功”。
4. 发布失败时能够将代码、数据库、文件和配置恢复到同一发布前时间点。
5. 正常情况下只保留最近 2 个已验证的发布恢复点。
6. 发布和回滚过程有清晰日志、清单、状态和人工确认点。

### 2.2 恢复目标

- **RPO**：从进入维护状态起不再接受业务写入，恢复点与发布前最后一笔已确认写入一致；按本流程回滚时，维护窗口内不会产生需要丢弃的新答卷。
- **RTO**：以生产库实际恢复演练结果为准；当前数据规模下目标为 15 分钟内恢复服务。
- 每次恢复演练都记录数据库导入耗时，数据增长后重新评估 RTO。

### 2.3 明确边界

本方案只在正式 ECS 本地磁盘保存备份，不使用 OSS 或其他异地副本。因此：

- 可以防止版本迁移失败、错误代码发布、数据库误修改和 Docker 卷误操作。
- 不能防止 ECS 整机丢失、云盘损坏、服务器被入侵后正式数据与本地备份同时被删除。
- 保留 2 个版本是满足近期版本回滚目标的最低配置，不属于完整灾难恢复方案。

## 3. 备份目录和恢复点结构

备份目录必须位于 Git 项目和 Docker 数据卷之外：

```text
/www/backup/survey-app/
├── releases/
│   ├── 20260828-143000_ded38b0/
│   │   ├── database.sql.gz
│   │   ├── backend-uploads.tar.gz
│   │   ├── minio-data.tar.gz
│   │   ├── environment.env
│   │   ├── docker-compose.yml
│   │   ├── manifest.json
│   │   ├── row-counts.tsv
│   │   ├── SHA256SUMS
│   │   ├── verify.log
│   │   └── STATUS
│   └── ...
├── failed-state/
└── logs/
```

目录名由“备份时间 + 升级前 Git 短提交号”组成，不允许自由文本进入目录名。

### 3.1 文件说明

| 文件 | 用途 |
| --- | --- |
| `database.sql.gz` | `survey_app` 完整逻辑备份，是数据库回滚的主要来源 |
| `backend-uploads.tar.gz` | 当前后端上传文件卷归档 |
| `minio-data.tar.gz` | MinIO 数据卷归档 |
| `environment.env` | 升级前生产环境变量，仅 root 可读 |
| `docker-compose.yml` | 升级前 Compose 源配置 |
| `manifest.json` | 时间、代码版本、镜像、MySQL、迁移和卷信息；只作为数据解析，禁止由 shell `source` 执行 |
| `row-counts.tsv` | 所有业务表的精确行数，用于恢复核对 |
| `SHA256SUMS` | 不可变备份载荷和清单的 SHA-256 校验值；不包含自身、`STATUS` 和持续追加的日志 |
| `verify.log` | 压缩包检查、临时恢复和行数核对结果 |
| `STATUS` | `CREATING`、`VERIFIED`、`RELEASE_SUCCEEDED` 或 `ROLLBACK_USED` |

### 3.2 权限

- `/www/backup/survey-app` 目录权限为 `700`。
- 所有备份文件权限为 `600`。
- 发布和恢复脚本只允许 root 或专门的运维账号执行。
- 数据库密码不能作为明文命令参数写入日志；通过受限权限配置文件或容器环境读取。
- `environment.env` 包含生产密钥，禁止提交 Git、发送聊天或写入普通发布日志。

## 4. Docker 卷识别

脚本不得硬编码本地环境的 `360-ccv2_*` 或正式环境可能使用的 `survey-app_*` 卷名。

每次备份通过当前 Compose 项目和容器挂载关系解析：

- MySQL 容器内 `/var/lib/mysql` 对应的实际卷。
- 后端容器内 `/app/uploads` 对应的实际卷。
- MinIO 容器内 `/data` 对应的实际卷。

解析结果写入 `manifest.json`。如果任一目标不是命名卷、出现多个候选或挂载目标与预期不同，备份必须停止并提示人工检查。

## 5. 发布前检查

发布脚本使用进程锁，保证同一时间只能运行一个备份、发布或回滚任务。

开始前必须检查：

1. 当前目录是 `/www/wwwroot/survey-app` 或显式配置的正式项目绝对路径。
2. Git 工作区没有未提交修改。
3. 当前提交和目标提交都存在，并记录完整 SHA。
4. MySQL、后端和必要的存储容器当前状态正常。
5. 数据库连接正常，`_prisma_migrations` 没有失败或未完成记录。
6. 备份账号具备读取表、视图、触发器、事件和存储过程所需权限。
7. 回滚维护账号具备创建和删除临时验证库及重建 `survey_app` 的权限。
8. 所有业务表使用支持一致性事务备份的 InnoDB 引擎；不满足时停止发布。
9. 三个持久化卷均能唯一解析。
10. 备份目录可写，权限正确。
11. 可用空间至少满足：数据库未压缩大小与文件卷总量的 3 倍，再预留 2 GB。
12. 当前存在的已验证备份能通过 `SHA256SUMS` 快速复检。

任一检查失败，发布立即停止，不能执行 Git 切换、容器重建或数据库迁移。

## 6. 每次生产发布的备份流程

### 6.1 进入维护状态

1. 获取发布锁。
2. 创建新的恢复点目录，`STATUS=CREATING`。
3. 记录当前 Git、容器、镜像、Compose、MySQL 和 Prisma 迁移状态。
4. 停止后端容器，阻止问卷、环评和上传继续写入。
5. 停止 MinIO 容器，确保对象卷归档一致。
6. 前端可以继续运行，但 Nginx 应显示维护提示或让 API 明确不可用。

### 6.2 数据库备份

MySQL 保持运行，使用事务一致性逻辑备份。标准参数至少包括：

```text
--single-transaction
--quick
--routines
--triggers
--events
--hex-blob
--default-character-set=utf8mb4
--no-tablespaces
```

备份通过管道压缩为 `database.sql.gz`。任何管道环节失败都必须被 `pipefail` 捕获，不能生成伪成功文件。

同时导出所有业务表的精确 `COUNT(*)` 和 `_prisma_migrations` 状态到 `row-counts.tsv` 与清单。

### 6.3 文件卷备份

- 后端停止后，以只读方式挂载 uploads 卷并归档为 `backend-uploads.tar.gz`。
- MinIO 停止后，以只读方式挂载 MinIO 卷并归档为 `minio-data.tar.gz`。
- 即使卷为空，也必须生成合法的空归档，保持恢复点结构一致。
- `node_modules`、前端构建产物、容器缓存和镜像层不属于业务数据，不进入备份。

### 6.4 配置和清单

- 复制升级前 `.env` 和 `docker-compose.yml`。
- 保存 Git 完整提交号、目标提交号、当前分支、MySQL 版本、Node 版本、Docker Compose 版本、镜像 ID、迁移版本和实际卷名。
- 不把解析后的完整 Compose 环境输出到普通日志，避免泄露环境变量。

### 6.5 保持维护状态

从停止后端写入开始，到备份验证完成且新版本冒烟验收通过为止，Nginx 持续展示维护页，后端和 MinIO 不重新对外提供写服务。这样可以保证恢复点之后没有新的正式答卷或附件，避免发布失败回滚时丢失维护窗口内的数据。

如果备份验证或后续发布失败，脚本切回升级前 Git 提交和配置，确认数据库与文件卷未被目标版本改动后，再恢复升级前服务。不能在验证期间短暂开放旧后端。

## 7. 备份验证门禁

新恢复点必须全部通过以下检查：

1. 所有必需文件存在且大小合理。
2. `gzip -t database.sql.gz` 通过。
3. 两个 tar 包都可以完整列出目录。
4. 对数据库、两个卷归档、环境和 Compose 配置、`manifest.json`、`row-counts.tsv` 生成并执行 `sha256sum -c SHA256SUMS`；可变的 `STATUS` 和日志不进入校验集。
5. 在同一 MySQL 实例创建随机命名的临时验证库；库名只允许脚本生成，且必须与 `survey_app` 明确不同。
6. `database.sql.gz` 不包含 `CREATE DATABASE` 或固定 `USE survey_app` 语句，把它完整导入临时验证库，确保验证过程不会写入正式库。
7. 核对所有业务表存在。
8. 核对每张表的精确行数与 `row-counts.tsv` 一致。
9. 核对 `_prisma_migrations` 记录数量、迁移名称和完成状态一致。
10. 记录恢复耗时和校验结果。
11. 无论成功或失败，都通过退出清理器删除临时验证库。

全部通过后，将 `STATUS` 原子更新为 `VERIFIED`。任何失败均执行：

- 保留失败恢复点和日志供排查。
- 不删除原有两个已验证恢复点。
- 不继续生产发布。
- 确认代码和配置仍指向升级前版本，再恢复升级前后端与 MinIO 服务。

## 8. 生产发布门禁

生产发布必须由统一脚本执行，不再直接使用裸命令：

```text
git pull
docker compose up -d --build
```

标准发布入口规划为：

```text
scripts/prod/release.sh <target-git-ref>
```

发布脚本只有在本次恢复点状态为 `VERIFIED` 时才允许：

1. 切换到目标 Git 提交。
2. 构建目标版本。
3. 启动服务并执行 `prisma migrate deploy`。
4. 检查后端健康接口和容器状态。
5. 检查迁移记录是否符合目标版本。
6. 执行管理员登录、普通问卷、360 环评和上传访问的最小冒烟测试。

冒烟验收通过后，恢复点状态更新为 `RELEASE_SUCCEEDED`。该状态表示“以此恢复点为发布前基线的目标版本已成功上线”，恢复点内容本身仍是升级前状态。

## 9. 滚动保留最近 2 个版本

“保留最近 2 个版本”指保留最近两个状态为 `RELEASE_SUCCEEDED` 或经负责人明确标记为可用的完整恢复点。它们分别对应最近两次成功发布之前的完整状态。

滚动规则：

1. 发布开始前如果已有 2 份恢复点，先创建第 3 份，暂时允许存在 3 份。
2. 新恢复点未验证前，不删除任何旧恢复点。
3. 新版本发布失败时，不执行自动清理。
4. 只有新版本冒烟验收通过并把新恢复点标记为 `RELEASE_SUCCEEDED` 后，才清理最旧恢复点。
5. `CREATING`、验证失败或事故现场备份不计入正常的 2 个版本，事故关闭前由人工处理。
6. 当前正在使用的回滚目标不能被自动删除。

清理脚本只允许删除 `/www/backup/survey-app/releases/` 下同时满足以下条件的单个目录：

- 解析后的绝对路径仍位于指定备份根目录内。
- 目录名符合固定时间戳和 Git SHA 格式。
- 存在合法清单和状态文件。
- 不是最近两个已验证恢复点。
- 不是当前发布或回滚任务引用的恢复点。

禁止使用未校验变量、通配符或宽泛路径执行递归删除。

## 10. 快速回滚触发条件

出现以下任一情况，应停止继续修补并进入标准回滚评估：

- Prisma 迁移失败或处于不确定状态。
- 新版本无法启动或健康检查持续失败。
- 管理端、填写端或企微登录核心流程不可用。
- 数据条数异常下降、历史问卷或环评数据不可读取。
- 新旧代码与数据库结构明显不兼容。
- 发布后出现错误写入，且无法用安全的前向修复立即解决。

如果新版本已经产生新的正式答卷，回滚到发布前恢复点会丢弃这些新数据，必须由负责人明确确认后执行。优先进入维护状态并导出一份失败现场备份，用于事后人工合并或追查。

## 11. 标准快速回滚流程

规划入口：

```text
scripts/prod/rollback.sh <backup-id>
```

回滚属于破坏性操作，必须显式指定恢复点并再次输入完整备份 ID 确认。流程如下：

1. 获取发布锁，阻止并发发布或再次回滚。
2. 验证目标路径、`STATUS`、清单和全部 SHA-256。
3. 显示将恢复的时间点、Git 提交、数据库迁移版本和数据行数。
4. 停止后端和 MinIO，关闭所有业务写入。
5. 正常受控发布中维护窗口不会产生新写入；如果因绕过门禁或发布后运行一段时间而已有新数据，必须先创建 `failed-state` 现场备份。无法创建现场备份时，必须由负责人明确接受数据丢失风险，否则停止回滚。
6. 切换代码到恢复点记录的升级前完整 Git 提交。
7. 还原恢复点的 `.env` 和 Compose 配置；如果配置没有变化，可以只校验不覆盖。
8. 删除并重新创建 `survey_app` 数据库。
9. 导入 `database.sql.gz`。
10. 清空并恢复 uploads 与 MinIO 卷内容。
11. 使用恢复点对应代码重新构建并启动容器。
12. 旧后端启动时只会看到恢复点数据库中的旧迁移记录，不应执行目标新版本迁移。
13. 核对核心表行数、迁移状态、健康接口和容器状态。
14. 执行管理员登录、历史问卷、历史答卷、联系人、360 批次和导出冒烟测试。
15. 回滚成功后将恢复点标记为 `ROLLBACK_USED`，记录操作人、原因和耗时。

如果数据库恢复成功但文件卷恢复失败，后端保持停止，不允许以数据库和附件时间点不一致的状态恢复业务。

## 12. 回滚后验收

必须检查：

- 管理员可以登录。
- 问卷、联系人、白名单、历史答卷数量与备份清单一致。
- 360 批次、人员快照、关系、答卷、结果和审计日志数量一致。
- 至少抽查一份普通问卷答卷和一份 360 个人报告。
- 现有附件 URL 可以访问。
- `_prisma_migrations` 没有失败记录，最后迁移与恢复点一致。
- 新版本新增字段或表不应残留在已经恢复的旧数据库中。
- Nginx、前端、后端、MySQL 和 MinIO 状态正常。

验收失败时继续保持维护状态，不能让员工重新写入。

## 13. 计划提供的运维脚本

| 脚本 | 职责 |
| --- | --- |
| `scripts/prod/preflight.sh` | 环境、磁盘、数据库、卷和迁移检查 |
| `scripts/prod/backup.sh` | 创建一致性恢复点 |
| `scripts/prod/verify-backup.sh` | 校验压缩包、哈希并临时恢复数据库 |
| `scripts/prod/release.sh` | 串联备份门禁和正式发布 |
| `scripts/prod/rollback.sh` | 按恢复点执行完整回滚 |
| `scripts/prod/list-backups.sh` | 安全列出备份状态和恢复信息 |
| `scripts/prod/prune-backups.sh` | 发布成功后保留最近两个恢复点 |

所有脚本必须：

- 使用严格错误模式和管道失败传播。
- 使用绝对路径和发布锁。
- 支持 `--dry-run` 查看将执行的操作。
- 输出结构化日志，但不打印密码和完整环境变量。
- 在退出处理器中恢复被暂停的服务和清理临时验证库。
- 对删除数据库、清空卷、覆盖 `.env` 和删除旧备份等操作要求明确确认。

## 14. 恢复演练与验收

脚本上线前先使用本地或脱敏副本完成演练：

1. 创建包含问卷、答卷、联系人、360 批次和附件的数据集。
2. 执行完整发布前备份。
3. 验证临时恢复数据库的所有表和行数。
4. 人为执行一个新增字段的测试迁移并写入测试数据。
5. 使用备份执行完整回滚。
6. 确认新增结构消失，历史数据、附件和代码全部恢复。
7. 测量并记录备份时间、维护窗口和恢复时间。
8. 模拟备份损坏，确认校验失败会阻止发布。
9. 模拟磁盘不足，确认发布在停止服务前失败。
10. 连续执行三次发布，确认仅在第三次成功后安全清理最旧恢复点。

首次正式上线备份脚本时，只创建和验证恢复点，不同时发布大版本。确认备份和恢复演练通过后，再把发布入口切换到 `release.sh`。

## 15. 方案完整性复核

| 风险 | 设计覆盖 |
| --- | --- |
| 数据库迁移失败 | 发布前逻辑备份与旧迁移记录恢复 |
| 代码与数据库不匹配 | 恢复点绑定完整 Git SHA 和数据库迁移版本 |
| 上传附件遗漏 | uploads 与 MinIO 两个卷均备份 |
| 备份损坏或不可恢复 | 哈希、压缩检查和临时库完整导入 |
| 备份时仍有写入 | 停止后端和 MinIO 后再采集恢复点 |
| 错误卷或新空卷 | 动态解析挂载并写入清单 |
| 新备份失败后旧备份被删 | 发布成功后才滚动清理 |
| 清理脚本误删宽泛目录 | 固定根目录、格式、状态和引用检查 |
| 密码泄露 | 受限文件、日志脱敏、不使用明文参数 |
| 回滚后数据库与附件不一致 | 数据库和两个文件卷作为同一恢复点整体恢复 |
| 回滚丢失发布后新数据 | 回滚前警告并保留失败现场备份 |
| 没人记得回滚方式 | 根目录项目规则强制指向本设计，所有操作以脚本和本文为准 |

复核结论：本方案完整覆盖“单机本地备份、每次生产发布、最近两个恢复点、数据库快速回滚”的目标。剩余风险是 ECS 整机或云盘损坏，这属于用户明确接受的不使用异地副本边界。

## 16. 强制运维规则

1. 禁止在正式服务器执行 `docker compose down -v`。
2. 禁止手工删除 MySQL、uploads 或 MinIO 卷。
3. 禁止绕过已验证备份直接执行生产数据库迁移。
4. 禁止只回滚 Git 而不核对数据库迁移版本。
5. 禁止把备份目录放进项目目录或提交 Git。
6. 禁止在备份未通过临时恢复测试时继续发布。
7. 回滚必须按本文和正式回滚脚本执行，不能临场拼接破坏性命令。

本文是后续备份脚本、发布脚本、回滚脚本、恢复演练和生产运维的唯一设计基线。
