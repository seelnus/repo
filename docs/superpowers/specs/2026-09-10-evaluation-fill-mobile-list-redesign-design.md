# 360 环评员工列表页移动端重设计

**日期**：2026-09-10

**状态**：设计已确认

**页面**：`/eval-fill`

**范围**：员工登录后的「待我填写」与「我的结果」两个页签

## 1. 背景与目标

当前 `/eval-fill` 使用桌面端卡片和横向任务行直接收缩到手机宽度。虽然功能可用，但移动端存在以下问题：

- 页面缺少清晰的员工身份和任务概览。
- 待填写与已完成任务混在同一批次卡片内，员工需要主动寻找下一项任务。
- 任务卡片的信息层级弱，关系类型、被评价人、批次与操作按钮竞争视觉焦点。
- 结果卡片在窄屏下只是机械换行，评分与归档状态不够突出。
- 加载、空状态和错误状态没有形成统一的移动端体验。

本次采用已确认的方案 A「待办优先工作台」，目标是让员工进入页面后立即知道：

1. 还有多少份评价要完成。
2. 哪一份最紧急。
3. 点击哪里开始填写。
4. 哪些个人归档结果可以查看。

本次只重设计员工列表入口页，不改具体答题页和个人结果详情页。

## 2. 设计原则

### 2.1 待办优先

待填写任务始终排在已完成任务之前，并按批次截止时间升序排列。已完成任务默认折叠，避免占据手机首屏。

### 2.2 一张卡只表达一个动作

每张待办卡片只保留关系类型、被评价人、问卷标题、批次、截止时间和「开始填写」按钮。主要按钮始终位于卡片右下区域，触控目标不小于 44px。

### 2.3 使用 Ant Design 语义

页面继续使用现有 Ant Design 体系：

- `Tabs`：切换「待我填写 / 我的结果」。
- `Badge`：显示待填写数量。
- `Card`：任务和归档结果容器。
- `Tag`：关系类型、紧急状态和归档状态。
- `Progress`：展示整体完成进度。
- `Button`：主要动作。
- `Collapse`：收起已完成任务。
- `Skeleton`、`Empty`、`Result`：加载、空状态和错误状态。

### 2.4 移动端优先但不破坏桌面端

核心 DOM 和数据逻辑共用，移动端在 `max-width: 768px` 下启用专用布局。桌面端继续保持居中的内容区域，并使用同一套信息层级，不能因本次修改产生功能回退。

## 3. 视觉系统

视觉基于 Ant Design 默认蓝色体系，避免另建一套品牌组件。

| 角色 | 色值 | 用途 |
| --- | --- | --- |
| 主色 | `#1677ff` | 主按钮、激活页签、进度 |
| 主色浅底 | `#e6f4ff` | 自评标签、身份头像、任务概览底色 |
| 成功色 | `#52c41a` | 已完成、已归档、100% 完成 |
| 警告色 | `#fa8c16` | 临近截止提示 |
| 危险色 | `#ff4d4f` | 72 小时内截止、待办数量徽标 |
| 页面背景 | `#f5f7fa` | 手机端页面底色 |
| 主文字 | `#1f1f1f` | 标题与任务名称 |
| 次文字 | `#8c8c8c` | 批次、时间与辅助说明 |

字体沿用系统中文字体和 Ant Design 默认字体栈。标题使用 18px/600，任务标题使用 15px/600，正文使用 13px，辅助信息使用 11–12px。

页面的识别元素是「任务行动条」：它不是装饰性横幅，而是集中表达待办数量、总进度和最近截止时间，作为进入页面后的首要行动提示。

## 4. 页面结构

### 4.1 顶部身份区

顶部采用紧凑白色导航区：

- 左侧：蓝色「评」标识、标题「360 环评」、副标题「员工任务中心」。
- 右侧：员工头像与姓名组成的身份胶囊。
- 点击身份胶囊打开 `Dropdown`，提供「切换身份」操作，复用现有登出逻辑。
- 员工姓名从当前 `fill_token` 的 `name` 声明读取；解析失败时显示「当前员工」。姓名只用于展示，不参与任何鉴权判断。

顶部身份区和页签在手机端保持粘性定位。页面滚动时，员工仍能看到当前身份和所在页签。

### 4.2 页签

两个页签为：

- `待我填写`：徽标显示尚未完成的任务数量。
- `我的结果`：加载后显示可查看的归档结果数量。

页签状态继续与 URL 同步：

- `/eval-fill` 对应 `tasks`。
- `/eval-fill?tab=results` 对应 `results`。

刷新页面或从个人结果详情返回时，应恢复正确页签。

## 5. 「待我填写」设计

### 5.1 任务行动条

行动条展示：

- 待完成任务数量。
- 已完成数量 / 总任务数量。
- Ant Design 环形 `Progress`。
- 最近一个有截止时间的批次截止日期。
- 当截止时间距离当前时间不超过 72 小时时，使用警告文案和危险色强调。

没有截止时间时，不显示虚构日期，改为「请按安排及时完成」。

### 5.2 待办任务

将后端返回的批次任务在前端扁平化为待办列表，同时保留批次信息。排序规则为：

1. 有截止时间的任务优先。
2. 截止时间越早越靠前。
3. 相同截止时间按批次 ID 倒序、关系 ID 升序保持稳定。
4. 无截止时间的任务排列在有截止时间任务之后。

每张待办卡片展示：

- 关系标签：本人自评、同事评价、领导评价等现有关系类型。
- 批次名称。
- 主标题：本人自评显示「完成本人自评」；其他关系显示「评价 {被评价人姓名}」。
- 问卷标题。
- 截止日期或剩余天数。
- 主按钮「开始填写」。

当前系统没有草稿保存能力，因此本次不使用「继续填写」文案，也不新增自动保存能力。

### 5.3 已完成任务

已完成任务放入 `Collapse`，默认折叠。折叠标题显示「已完成的评价」和完成数量。展开后展示只读任务行与绿色「已完成」标签，不提供重复进入或重复提交入口。

### 5.4 空状态

- 完全没有任务：显示 `Empty`，文案为「当前没有需要填写的环评」。
- 所有任务都已完成：行动条显示完成状态，待办区域显示「本轮任务已全部完成」，已完成区域仍可展开查看。

## 6. 「我的结果」设计

### 6.1 结果概览

顶部展示浅绿色状态条：

- 可查看的归档结果数量。
- 辅助文案「归档后可查看本人评分汇总」。

紧接着展示隐私说明：仅展示员工本人作为被评价人的汇总评分，不展示评价人身份、文字反馈、案例或原始答卷。

### 6.2 归档结果卡片

按归档时间倒序展示，每张卡片包含：

- 批次名称。
- 「已归档」标签。
- 归档时间。
- 最终总分，保留两位小数。
- 已收 / 应收数量。
- 完成度百分比。
- 「查看个人结果」按钮。

当 `resultAvailable=false` 时，总分显示 `—`，按钮禁用并显示「暂无结果」。点击可用结果进入现有 `/eval-fill/results/:cycleId`。

### 6.3 加载、错误与空状态

- 首次进入结果页签：使用两张 `Skeleton` 结果卡片，避免只显示居中的转圈。
- 接口失败：使用 `Result status="warning"`，明确显示错误信息并提供「重新加载」。
- 没有归档结果：使用 `Empty`，文案为「暂无可查看的个人环评结果」。
- 401：清理填写端令牌并返回登录状态，沿用现有行为。

## 7. 数据与接口调整

本次不新增数据库表、不修改 Prisma Schema，也不新增接口。

现有 `GET /api/eval/tasks` 的每个批次对象增加一个字段：

```json
{
  "cycleId": 4,
  "cycleName": "2026 Q2 360环评",
  "cycleStatus": "published",
  "cycleEndAt": "2026-09-18T15:59:59.000Z",
  "tasks": []
}
```

`cycleEndAt` 直接来自 `EvalCycle.endAt`。它仅用于员工端展示和排序，不改变后端的可填写时间校验。

「我的结果」继续使用现有员工专用接口：

- `GET /api/eval/archived-results`
- `GET /api/eval/archived-results/:cycleId`

员工姓名从已有填写端 JWT 的 `name` 声明解析，仅作为非可信展示信息。所有数据权限仍由后端 `FillAuthGuard` 和员工专用查询条件控制。

## 8. 前端组件边界

为避免继续扩大 `EvalPages.tsx` 中的单体页面，移动端列表相关展示拆成以下内部组件或独立文件：

- `EvalFillHeader`：标题、身份胶囊和切换身份。
- `EvalFillTabs`：页签及 URL 状态同步。
- `EvalTaskOverview`：待办数量、进度和最近截止时间。
- `EvalPendingTaskCard`：单个待办任务。
- `EvalCompletedTasks`：已完成任务折叠区。
- `EvalArchivedResultCard`：单个归档结果。
- `eval-fill-view-model`：扁平化、计数、截止时间与排序等纯函数。

页面容器只负责数据加载、401 处理、页签状态和进入答题/结果详情的导航。

## 9. 响应式规则

### 手机端（不大于 768px）

- 页面宽度占满视口，外边距为 12–14px。
- 顶部身份区和页签粘性定位。
- 任务卡片单列展示。
- 主按钮最小高度 44px，卡片左右内边距 14px。
- 长批次名、员工名和问卷标题允许换行，不使用横向滚动。
- 安全区域底部增加 `env(safe-area-inset-bottom)`。

### 桌面端（大于 768px）

- 内容最大宽度保持 720px。
- 顶部不强制粘性定位。
- 卡片信息可横向排列，但操作与手机端保持一致。

## 10. 异常与边界情况

- `cycleEndAt` 为空：不参与紧急排序，显示通用完成提示。
- 截止时间已经过去但任务仍由接口返回：显示红色「已到截止时间」，不在前端擅自隐藏；后端仍负责最终是否允许填写。
- 待办数量超过 99：徽标显示 `99+`。
- 员工姓名解析失败：显示「当前员工」，切换身份仍可用。
- 结果总分为空：显示 `—`，不转换成 `0.00`。
- `expectedCount=0`：完成度显示 `—`，避免除零。
- 长文本：批次名最多显示两行；问卷标题最多显示两行；不影响按钮触控区域。

## 11. 验收标准

### 功能

1. `/eval-fill` 默认进入「待我填写」。
2. 待办数量、已完成数量和总进度计算正确。
3. 待办按截止时间排序，已完成任务默认折叠。
4. 点击「开始填写」进入正确的关系任务。
5. 切换到「我的结果」后加载归档结果，刷新仍保持结果页签。
6. 点击「查看个人结果」进入对应员工个人结果详情。
7. 切换身份会清除任务和结果缓存并返回登录状态。

### 视觉与移动端

1. 在 320px、375px、390px 和 430px 宽度下无横向滚动。
2. 主操作按钮与身份操作触控区域不小于 44px。
3. 紧急、普通、已完成、已归档和不可用状态可明确区分。
4. iPhone 安全区域不会遮挡页面内容。
5. 桌面端现有功能不回退。

### 安全与隐私

1. 页面仍只能读取当前填写端用户的数据。
2. 员工姓名的前端解析不参与权限判断。
3. 结果列表和详情不展示评价人身份、文字反馈、案例或原始答卷。

## 12. 测试策略

- 后端单元测试：验证 `GET /api/eval/tasks` 返回 `cycleEndAt`，且仍只查询当前评价人的已发布任务。
- 前端纯函数测试：验证待办/已完成拆分、截止时间排序、紧急状态和完成度计算。
- 前端构建检查：TypeScript 和 Vite 构建通过。
- 响应式人工验收：使用 320px、375px、390px、430px 和桌面宽度检查布局。
- 交互验收：页签、折叠、开始填写、查看结果、重新加载和切换身份均可用。
- 回归验收：实际提交一份 360 环评，返回列表后任务进入已完成折叠区；员工个人结果权限不变。

## 13. 不在本次范围

- 具体答题页的手机端重设计。
- 草稿保存或自动保存。
- 消息提醒、倒计时通知和推送。
- 个人结果详情页的重新设计。
- 新增评价数据、修改评分逻辑或改变归档权限。
