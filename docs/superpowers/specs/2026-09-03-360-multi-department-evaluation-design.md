# 360 多部门互评接入设计

**日期**：2026-09-03
**状态**：用户已确认数据方案、关系生成规则和页面流程
**范围**：只改造新建或重新确认人员的 V2 360 草稿批次；不改写历史批次

## 1. 背景与问题

通讯录已支持员工一个主部门、多个兼任部门，并为每条兼任归属保存“默认参加该部门互评”。当前 360 批次确认人员时仍只复制 `Contact.department`，每个 `EvalCycleParticipant` 只有一个 `groupKey`。关系生成器也只按该单一小组分组，因此不会消费已开启互评的兼任部门。

已验证的典型场景：

- 丁史远的主部门是“查曌激活组”。
- 查曌的主部门是“查曌组”，兼任“查曌激活组”且已开启互评。
- 当前批次只保存了两人的主部门小组，所以只生成了自评，没有生成双向互评。

## 2. 设计目标

1. 一名普通参评人员可以同时进入多个当期互评小组。
2. 主部门默认且强制参加；兼任部门继承通讯录的默认互评开关。
3. 批次使用快照，确认人员后不随通讯录调岗、部门改名或开关变化而静默改变。
4. 每人只有一条自评；同一对人通过多个小组相遇时，每个方向只保留一条互评关系。
5. 当期可在不回写通讯录的前提下，对已有兼任部门的互评开关做临时调整。
6. 关系复核能够解释每条自动关系来自哪个或哪些小组。

## 3. 不在本次范围

- 不改写已发布、已关闭或已有答卷的批次。
- 不让批次动态跟随实时通讯录。
- 不开发通用规则引擎、权重配置或基于职级的方向规则。
- 不允许在当期小组调整中为员工添加通讯录中不存在的部门归属；任意跨组单人关系继续使用人工关系。
- 特殊人员继续使用现有人工配置，不进入普通自动小组生成。

## 4. 数据模型

### 4.1 新增 `EvalParticipantGroupSnapshot`

每条记录表示一名批次参评人员在确认时的一条部门小组快照。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `participantId` | 关联 `EvalCycleParticipant` |
| `departmentId` | 确认时的组织部门 ID |
| `departmentCodeSnapshot` | 确认时的稳定部门编码 |
| `departmentNameSnapshot` | 确认时的末级部门名称 |
| `departmentPathSnapshot` | 确认时的完整部门路径 |
| `isPrimarySnapshot` | 当时是否为主部门 |
| `evalEnabled` | 当期是否参加该小组互评 |
| `roleNameSnapshot` | 确认时在该部门的组织职责 |
| `createdAt` / `updatedAt` | 创建和调整时间 |

约束与索引：

- `participantId + departmentId` 唯一。
- `participantId` 删除时快照级联删除。
- `departmentId` 关联组织部门并使用 `onDelete: Restrict`；部门删除校验必须把批次小组快照计入历史引用，避免丢失稳定的小组身份。
- 建立 `departmentId + evalEnabled` 和 `participantId + evalEnabled` 索引，支持分组生成和页面查询。
- 主部门快照的 `evalEnabled` 必须为 `true`，由服务层在事务中强制。
- 名称和路径使用快照字段，后续部门改名或移动不改写历史批次。

### 4.2 保留现有字段

`EvalCycleParticipant.departmentSnapshot` 、`groupKey` 和 `groupName` 继续保留，并记录主部门快照，供历史页面和旧数据兼容。新的 V2 关系生成器以 `EvalParticipantGroupSnapshot` 为准，不再只依赖单一 `groupKey`。

### 4.3 关系来源解释

不为每个共同小组重复创建 `EvalRelation`。关系仍使用现有 `cycleId + raterContactId + rateeContactId` 唯一约束去重。查询关系明细时，基于两人的批次小组快照求交集，返回稳定的“共同小组”来源列表。人工关系保持“人工”来源，不伪造组织来源。

## 5. 批次快照流程

### 5.1 候选人员

- 仅返回启用联系人。
- 同时返回主部门和全部兼任部门关系。
- 按部门筛选时，匹配员工的任一启用归属；同一员工不会被重复勾选。

### 5.2 确认人员范围

后端在单个数据库事务中：

1. 验证批次仍为草稿且没有已提交答卷。
2. 读取所选联系人的基础资料、启用状态、主部门和全部兼任部门。
3. 替换当前批次的参评人员快照和小组快照。
4. 主部门记为当期强制参加；兼任部门的 `evalEnabled` 继承 `defaultEvalEnabled`。
5. 删除当前批次的旧自动关系；人工关系仅在评价人与被评价人都仍属于新参评范围时保留，涉及已移除人员的人工关系同步删除。保存后要求管理员重新生成并复核关系。
6. 记录审计日志，包含参评人员数、快照小组数和多小组人员数。

已发布、已关闭或已有答卷的批次禁止重新确认。通讯录变化不自动进入已有批次；管理员必须主动重新确认。

### 5.3 当期调整

- 主部门开关只读且保持开启。
- 兼任部门可在草稿批次中单独开启或关闭当期互评。
- 当期调整只修改快照表，不回写 `ContactDepartmentMembership`。
- 已经生成但尚未作答的自动关系在小组开关变化后标记为需要重新生成，不在页面背景中静默改写。

## 6. 关系生成规则

V2 自动生成器改为以“参评人员 + 开启的小组快照”为输入：

1. 只处理 `mode=normal` 的参评人员。
2. 先为每个普通人员生成一条自评。
3. 按 `departmentId` 对 `evalEnabled=true` 的小组快照分组。
4. 每个小组内，为任意两个不同员工生成双向互评候选。
5. 使用 `raterContactId + rateeContactId` 键去重，一对人在多个共同小组中仍只保留每个方向一条关系。
6. 继续只删除和重建 `source=auto` 的关系，人工关系不被自动生成器覆盖。
7. 若人工关系已占用同一方向，自动生成候选跳过该键，保留人工关系。

单人小组只不产生互评，不影响该员工通过其他小组生成互评。

### 6.1 示例

丁史远的当期小组：

- 主·查曌激活组（开启）

查曌的当期小组：

- 主·查曌组（开启）
- 兼·查曌激活组（开启）

生成结果：

- 丁史远自评。
- 查曌自评。
- 丁史远评价查曌，来源“查曌激活组”。
- 查曌评价丁史远，来源“查曌激活组”。

## 7. 页面与交互

### 7.1 参评人员列表

将现有单一“部门/组”列调整为“当期互评小组”：

- 主部门使用绿色标签，如“主·查曌组”。
- 已开启的兼任部门使用蓝色标签，如“兼·查曌激活组”。
- 列表最多直接展示三个标签，其余显示“+N”并通过提示展示。
- 未开启的兼任部门放在调整抽屉中，不占用表格主视图。

每行增加“调整小组”操作：

- 使用 Ant Design Drawer、Tag、Switch 和 Alert。
- 主部门开关锁定开启。
- 兼任部门允许仅对当前草稿批次切换。
- 抽屉明确提示“仅影响当前批次，不修改通讯录”。

### 7.2 确认人员范围

确认前使用 Ant Design Modal 展示：

- 参评人员总数。
- 当期小组总数。
- 同时进入多个小组的人数。
- 单人小组数和名单。
- 若已有未作答关系，明确提示快照替换后需要重新生成关系。

新增人员不需要逐条确认；该弹窗是整个批次快照替换的一次确认。

### 7.3 关系复核

- 自动关系的来源显示“自动·小组名”。
- 一对人共享多个小组时展示多个来源标签，但只显示一条评价任务。
- 人工关系仍显示“人工”。
- 生成结果展示参评人数、自评数、去重后互评数、覆盖小组数以及异常清单。

## 8. 接口变更

### 8.1 候选人员与批次快照

- `GET /api/admin/eval/participant-candidates` 增加返回联系人的部门归属、完整路径、主/兼任类型和默认互评开关。
- `PUT /api/admin/eval/cycles/:id/participants` 在替换人员快照时同时替换小组快照。
- `GET /api/admin/eval/cycles/:id/participants` 返回每名参评人员的全部小组快照。
- 新增 `PUT /api/admin/eval/cycles/:id/participants/:participantId/groups`，只允许调整已快照兼任部门的 `evalEnabled`。

### 8.2 预览与关系

- 确认人员前由后端返回快照摘要和阻断错误，前端不自行推测小组数。
- 关系生成接口保持现有地址，内部改用多小组快照生成。
- 关系列表接口增加 `sharedGroups`，由后端基于批次快照计算。

## 9. 错误处理与安全边界

确认人员时遇到以下情况阻止保存，并返回具体员工和原因：

- 联系人已停用。
- 没有主部门或存在多个主部门。
- 主部门已停用、不存在或已变成非末级部门。
- 同一员工重复归属同一部门。

兼任部门已停用时，其快照保留但当期默认关闭互评，并在确认摘要中警告。已有答卷时，重新确认人员、调整小组和重新生成关系均被后端禁止，不只依赖前端按钮禁用。

## 10. 兼容与迁移

1. 新迁移只创建小组快照表和索引，不改写任何现有批次、参评人、关系、答卷或结果。
2. 历史批次没有小组快照时，查询页面继续使用原 `groupName`。
3. 新建 V2 草稿批次在首次确认人员时写入多小组快照。
4. 已有 V2 草稿批次不自动回填；管理员主动重新确认人员后才进入新逻辑。
5. 当前“测试全公司环评”批次需要重新确认人员范围，然后重新生成关系；不直接修改数据库关系。

## 11. 测试与验收

### 11.1 后端单元测试

- 主部门强制开启，兼任部门继承默认开关。
- 普通员工一个主部门、多个兼任部门快照。
- 多个小组内的双向互评生成。
- 共享多个小组时双向关系分别去重。
- 每人只有一条自评。
- 特殊人员不进入普通自动生成。
- 人工关系不被重新生成覆盖。
- 共同小组来源计算正确。

### 11.2 后端集成测试

- 确认人员在单个事务中替换人员和全部小组快照。
- 确认后更改通讯录，现有批次快照和关系不变。
- 草稿批次重新确认后继承最新通讯录开关。
- 已有答卷时三个写操作全部被阻止。
- 老批次无新快照数据仍可正常查询。

### 11.3 前端验收

- 人员列表正确展示主部门和开启的兼任部门标签。
- 抽屉可以仅对当期切换兼任部门互评。
- 重新确认人员前显示准确的人员、小组和单人组摘要。
- 关系复核能展示自动关系的全部共同小组来源。
- 丁史远和查曌形成双向互评，且两人各只有一条自评。

## 12. 本地验证顺序

1. 执行 Prisma 生成和新迁移。
2. 运行多小组快照与关系生成单元测试。
3. 运行后端完整测试和构建。
4. 运行前端构建。
5. 在本地“测试全公司环评”批次中，由管理员重新确认人员并生成关系。
6. 验证丁史远→查曌、查曌→丁史远和双方自评关系，同时检查关系来源标签。
7. 验证历史批次、旧关系、答卷和统计报告未被改写。

## 13. 验收标准

1. 新确认的 V2 草稿批次能完整复制所选员工的主部门和全部兼任部门快照。
2. 只有主部门和开启互评的兼任部门参与自动生成。
3. 多小组员工在每个开启小组中均参与双向互评。
4. 一名员工只有一条自评，一个有向人员对只有一条互评。
5. 页面能解释人员的当期小组和自动关系来源。
6. 草稿批次可临时调整已有兼任部门的当期互评开关，且不回写通讯录。
7. 历史批次及其答卷、关系和结果不发生数据变化。
8. 当前测试批次在管理员主动重新确认和生成后，丁史远与查曌形成双向互评。
