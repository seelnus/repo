# 360 环评员工个人结果查看设计

## 背景

当前员工端“360 环评填写入口”只展示处于已发布状态、需要当前员工填写的评价任务。管理员端已有个人报告，可查看总得分、维度得分、逐题得分、案例说明和文字反馈，但员工无法在环评结束后查看自己的最终评分。

本次新增员工个人结果查看能力。员工只能查看自己作为被评价人的已归档批次，并且只能查看汇总评分，不得接触其他评价人的身份、案例说明、文字反馈或原始答卷。

## 目标

- 在现有员工填写入口增加“我的结果”标签页。
- 只展示当前登录员工本人作为被评价人的已归档环评批次。
- 提供员工专用结果接口，从服务端仅返回允许公开的评分汇总。
- 个人结果的评分口径与管理员个人报告一致。
- 不影响现有填写任务、管理员个人报告和统计导出。

## 非目标

- 不允许员工查看未归档批次的暂定结果。
- 不允许员工查看其他员工的结果。
- 不展示评价人姓名、评价关系明细或单个评价人的原始评分。
- 不展示案例说明、填空题文字反馈或原始答案，包括员工本人填写的文字内容。
- 不提供个人结果导出或公开分享链接。
- 不新增数据库表或数据库迁移。

## 可见范围与权限规则

员工能看到一个批次，必须同时满足：

1. 当前填写身份令牌有效。
2. 批次状态为 `archived`。
3. 批次参与人中存在 `contactId = 当前登录员工 ID` 的记录。
4. 员工是该批次的被评价人，而不是仅作为评价人出现。

员工查看某个批次详情时，后端必须再次执行以上校验，不能依赖列表结果或前端隐藏。

客户端不得提交被评价人 ID。后端始终从填写身份令牌中的 `fillUser.sub` 获取当前员工 ID，防止通过篡改请求查看其他员工结果。

对不存在、未归档、员工未参与或员工无权查看的批次，详情接口统一返回：

```text
个人环评结果不存在或暂不可查看
```

统一错误信息避免向员工泄露批次是否存在及其他员工是否参与。

## 员工填写入口

### 页面导航

现有 `/eval-fill` 页面顶部改为两个标签页：

- 待我填写
- 我的结果

“切换身份”保留在页面右上角。

### 待我填写

继续使用现有填写任务接口和页面内容，只展示处于已发布状态且在填写时间范围内的任务。本次不修改任务列表和提交逻辑。

### 我的结果

切换到“我的结果”时才请求员工归档结果列表，避免影响现有填写入口加载。

列表按 `archivedAt` 倒序排列。每个批次卡片展示：

- 批次名称。
- “已归档”状态标签。
- 归档时间。
- 最终总得分。
- 已收/应收。
- “查看个人结果”按钮。

如果员工没有可见的归档结果，显示：

```text
暂无可查看的个人环评结果
```

如果归档批次意外缺少员工结果记录，卡片仍显示批次信息，并显示不可点击的“暂无结果”，便于识别历史数据异常。

## 个人结果页面

个人结果使用独立路由：

```text
/eval-fill/results/:cycleId
```

页面包含：

1. “返回我的结果”按钮。
2. 批次名称。
3. “已归档”状态。
4. 当前员工姓名。
5. 最终总得分。
6. 已收/应收。
7. 维度得分表。
8. 逐题得分表。
9. 隐私说明：“结果仅展示汇总评分，不展示评价人身份及文字反馈”。

逐题得分表展示：

- 题目名称。
- 自评分。
- 他评平均分。
- 综合分。
- 有效答案数。

空分值统一显示“—”。分数沿用管理员个人报告的两位小数展示规则。

个人结果页不渲染案例说明和文字反馈组件。手机端允许表格横向滚动，汇总卡片按可用宽度换行，不能产生页面级横向溢出。

## 员工专用接口

员工接口继续放在现有 `EvalFillController` 下，并使用 `FillAuthGuard`。

### 获取已归档结果列表

```http
GET /api/eval/archived-results
```

响应仅包含当前员工可见的批次：

```ts
type ArchivedResultListItem = {
  cycleId: number;
  cycleName: string;
  archivedAt: string;
  resultAvailable: boolean;
  totalScore: number | null;
  receivedCount: number;
  expectedCount: number;
};
```

查询以 `EvalCycleParticipant.contactId = fillUser.sub` 为入口，并限制关联批次状态为 `archived`。通过 `cycleId + rateeContactId` 读取 `EvalEmployeeResult`。

### 获取个人评分汇总

```http
GET /api/eval/archived-results/:cycleId
```

响应结构：

```ts
type ArchivedPersonalResult = {
  cycle: {
    id: number;
    name: string;
    status: 'archived';
    archivedAt: string;
  };
  participant: {
    contactId: number;
    name: string;
  };
  result: {
    totalScore: number | null;
    receivedCount: number;
    expectedCount: number;
    dimensionScores: Array<{
      dimensionId: string;
      name: string;
      score: number | null;
    }>;
    questionScores: Array<{
      questionId: string;
      label: string;
      selfScore: number | null;
      otherScore: number | null;
      score: number | null;
      answerCount: number;
    }>;
  };
};
```

员工专用接口只读取 `EvalCycle`、`EvalCycleParticipant` 和 `EvalEmployeeResult`。它不得查询或返回 `SurveyResponse`、评价关系详情、案例说明或文字反馈。

不得直接复用管理员 `GET /api/admin/eval/cycles/:id/results/:contactId` 的响应，因为该接口会包含案例说明和文字反馈。员工接口可以复用评分字段映射辅助函数，但必须拥有独立的安全响应结构。

## 数据流

1. 员工通过现有企业微信填写身份登录。
2. 员工进入 `/eval-fill`，默认查看“待我填写”。
3. 员工切换到“我的结果”。
4. 前端请求 `GET /api/eval/archived-results`。
5. 后端根据 `fillUser.sub` 查询员工本人参与的已归档批次及最终结果。
6. 员工点击“查看个人结果”，进入 `/eval-fill/results/:cycleId`。
7. 前端请求 `GET /api/eval/archived-results/:cycleId`。
8. 后端重新校验身份、批次状态和参与人，返回最小评分汇总。
9. 前端渲染汇总卡片、维度得分和逐题得分。

个人结果页的返回按钮固定跳转到 `/eval-fill?tab=results`，确保返回后“我的结果”标签仍被选中。直接访问或刷新不带 `tab` 参数的 `/eval-fill` 时，默认进入“待我填写”。

## 生命周期约束

现有生命周期要求批次只有在结果已锁定后才能归档：

```text
closed → locked → archived
```

因此员工个人结果只展示最终结果，不触发重新计算，也不处理暂定状态。员工查看行为不得修改结果、批次或任何答卷。

## 异常处理

- 登录令牌缺失或过期：沿用现有填写端逻辑，清除本地填写令牌并返回登录页。
- 列表加载失败：显示错误提示，并提供“重新加载”按钮。
- 详情加载失败：显示统一的不可查看结果页，并提供返回按钮。
- 已归档但结果缺失：列表显示“暂无结果”，禁用详情按钮。
- 结果中的分数为空：使用“—”展示，不推断或补算分数。
- 前端不得把接口错误替换成管理员报告接口重试。

## 隐私与安全

- 身份来源只能是服务端验证后的填写身份令牌。
- 详情接口路径仅包含批次 ID，不包含员工 ID。
- 每次详情请求都校验员工本人是否是该批次参与人。
- 只有 `archived` 状态允许返回结果。
- 接口响应不得包含评价人、评价关系、案例、文字题答案或原始答卷。
- 前端隐藏不是安全边界，敏感字段必须在服务端响应之前剔除。
- 无权限与不存在使用相同错误信息，避免对象存在性探测。

## 测试方案

### 后端权限测试

- 已归档且当前员工是被评价人的批次出现在列表中。
- 当前员工只作为评价人、但不是批次参与人时，批次不出现在列表中。
- `draft`、`published`、`closed` 和 `locked` 批次不出现在列表中。
- 员工可以读取本人归档批次详情。
- 修改 URL 中的批次 ID 后，不能读取其他员工或非归档批次。
- 无权限、不存在和非归档详情返回统一错误。
- 未登录不能访问列表和详情。

### 后端数据最小化测试

- 列表和详情不包含评价人信息。
- 详情不包含 `cases`、`textFeedback`、`answersJson` 或原始关系数据。
- 详情评分字段与同批次管理员个人报告的评分字段一致。
- 详情请求不查询 `SurveyResponse`。
- 结果缺失时列表返回 `resultAvailable: false`。

### 前端测试

- 填写入口显示“待我填写 / 我的结果”两个标签。
- 默认进入“待我填写”，原有任务展示和提交功能正常。
- “我的结果”按归档时间倒序展示卡片。
- 无结果时显示正确空状态。
- 缺少结果记录时显示禁用的“暂无结果”。
- 点击按钮进入对应个人结果页。
- 返回后仍显示“我的结果”标签。
- 个人结果页只展示评分汇总和隐私说明。
- 手机宽度下表格可横向滚动且页面不横向溢出。

### 回归测试

- 企业微信登录、本地测试身份登录、切换身份保持正常。
- 现有待填写任务加载、填写与提交保持正常。
- 管理员个人报告仍显示完整案例说明和文字反馈。
- 管理员结果列表、结果锁定、归档与 Excel 导出保持正常。

## 验收标准

1. 员工填写入口具有“待我填写 / 我的结果”双标签页。
2. “我的结果”只展示当前员工本人作为被评价人的已归档批次。
3. 每个有结果的批次可以进入独立个人结果页。
4. 员工个人结果与管理员个人报告的评分汇总一致。
5. 接口和页面均不包含评价人身份、案例说明、文字反馈和原始答案。
6. 非归档批次、其他员工结果和未授权请求均无法访问。
7. 现有填写任务和管理员报告功能不受影响。
