# 360 环评发布后补充成员设计

**日期**：2026-09-10  
**状态**：交互方案已确认，待用户书面复核  
**范围**：V2 360 环评批次在已发布、未截止状态下增量补充普通参评成员

## 1. 背景

当前批次发布后，“参评人员”页面进入只读状态，后端也只允许草稿批次替换人员快照和重新生成自动关系。管理员若在发布后发现遗漏成员，只能重新建立批次，无法安全补充人员。

本功能允许管理员在批次已经有人提交问卷的情况下补充成员。补人必须采用增量方式，任何已有人员快照、评价关系和答卷都不得删除或改写。

## 2. 已确认规则

1. 只允许 `published` 且当前时间未超过 `endAt` 的 V2 批次补人。
2. `draft` 批次继续使用现有“确认人员范围”；`closed`、`locked`、`archived` 批次禁止补人。
3. 支持一次补充一名或多名普通成员。
4. 新成员完整加入原互评规则：生成自评，并与所有共享已启用当期小组的普通成员建立双向互评。
5. 已有答卷不阻止补人。系统只新增涉及新成员的缺失关系，不更新或删除任何已有关系与答卷。
6. 补人后，部分原成员会出现新的待办评价任务，这是预期行为。
7. 新成员的小组信息取确认补人时的通讯录快照；后续通讯录变化不会静默修改本批次。
8. 本功能不处理特殊人员、领导人工关系或批次成员删除。

## 3. 方案选择

采用“人员快照追加 + 自动关系差量插入”。系统先基于补人后的完整人员集合计算理论自动关系，再限制为“评价人或被评价人属于本次新增人员”的关系，并排除数据库中已经存在的有向人员对，最后只插入差集。

不采用以下方案：

- 不将已发布批次退回草稿，因为全量重生成可能改变已有任务和答卷口径。
- 不要求管理员逐条添加人工关系，因为操作量大且容易遗漏双向任务。
- 不复用现有“替换人员范围”接口，因为它会删除旧自动关系和重建人员快照。

## 4. 后端设计

### 4.1 独立服务边界

新增三个职责清晰的服务步骤：

1. `validatePublishedParticipantAddition`：验证批次、时间、联系人和重复成员。
2. `previewPublishedParticipantAddition`：构建候选人员快照并计算增量关系，仅返回影响摘要，不写库。
3. `addPublishedParticipants`：在单个事务中再次验证、追加人员与小组快照、插入增量关系并写审计日志。

预览和正式执行共享同一套纯计算逻辑，避免页面显示的影响范围与实际写入不一致。

### 4.2 接口

新增：

- `POST /api/admin/eval/cycles/:id/participants/additions/preview`
- `POST /api/admin/eval/cycles/:id/participants/additions`

请求体：

```json
{
  "contactIds": [352, 353]
}
```

预览返回：

```json
{
  "cycleId": 6,
  "newParticipantCount": 2,
  "selfRelationCount": 2,
  "peerRelationCount": 18,
  "affectedExistingRaterCount": 4,
  "totalRelationCount": 20,
  "deadlineAt": "2026-09-29T16:00:00.000Z",
  "participants": [
    {
      "contactId": 352,
      "name": "示例员工",
      "department": "闯货/员工私人号/技术部"
    }
  ],
  "warnings": []
}
```

正式执行返回同一摘要，并增加实际创建数量：

```json
{
  "createdParticipantCount": 2,
  "createdRelationCount": 20
}
```

### 4.3 状态与参数校验

后端必须校验：

- 批次存在、`version >= 2`、状态为 `published`。
- 批次具有有效的 `templateSurveyId`、`startAt` 和 `endAt`。
- 当前时间不晚于 `endAt`。
- `contactIds` 为去重后的正整数数组且至少包含一项。
- 联系人存在并处于启用状态。
- 联系人尚未属于当前批次；已存在的 ID 返回“员工已在当前批次中”，不静默跳过。
- 每位联系人具有唯一且启用的主部门；兼任部门沿用当前通讯录中的互评开关。

正式执行必须在事务内重新完成这些校验，防止预览后批次截止、联系人停用或被另一管理员先行加入。

### 4.4 快照追加

沿用现有 `planParticipantSnapshots` 规则为新联系人生成 `EvalCycleParticipant` 和 `EvalParticipantGroupSnapshot`：

- 新成员默认 `mode=normal`、`peerExempt=false`。
- 主部门强制 `evalEnabled=true`。
- 兼任部门继承 `defaultEvalEnabled`。
- `departmentSnapshot`、`groupKey` 和 `groupName` 保存主部门快照，兼容现有查询。
- 只创建本次新增成员，不重建原成员快照。

本功能不需要数据库迁移。

### 4.5 增量关系计算

1. 读取当前批次全部原成员及其小组快照。
2. 将本次新成员快照加入内存集合，调用现有 `buildMultiGroupAutoRelations` 计算理论关系。
3. 只保留 `raterContactId` 或 `rateeContactId` 属于本次新增人员的关系。
4. 读取批次已有全部关系键 `raterContactId:rateeContactId`，排除已经存在的自动或人工关系。
5. 使用批次统一模板创建剩余关系，字段为 `source=auto`、`status=pending`。
6. 数据库唯一约束和 `createMany(skipDuplicates=true)` 作为并发下的最后保护。

该规则会创建：

- 每位新普通成员的一条自评。
- 共享任一启用小组的新成员之间的双向互评。
- 共享任一启用小组的新成员与原普通成员之间的双向互评。

不会补建与新成员无关的旧缺失关系，也不会自动创建领导评价关系。

### 4.6 事务与审计

正式执行在单个 Prisma 事务内完成：

1. 重新读取并校验批次状态和截止时间。
2. 检查所有目标联系人仍未加入。
3. 创建新成员及小组快照。
4. 创建增量自动关系。
5. 写入 `EvalAuditLog`，动作名为 `add_published_participants`。

审计内容包含新增联系人 ID、人员数、自评数、互评数、受影响原评价人数、创建关系数、操作前批次成员数和关系数。不得写入问卷答案或其他敏感反馈。

## 5. 前端设计

### 5.1 入口

“人员与关系 → 参评人员”页面按状态展示操作：

- `draft`：保留“确认人员范围”。
- `published` 且未截止：展示“补充成员”。
- 其他状态：不展示补人操作，人员表保持只读。

补人入口与原人员范围操作分开，避免管理员误以为会替换全体成员。

### 5.2 选择与预览

使用 Ant Design `Modal`、`Select`、`Alert`、`Statistic` 和 `Tag`：

1. 点击“补充成员”打开选择弹窗。
2. 候选列表排除已经在本批次中的成员，支持搜索和多选。
3. 选项展示“姓名 · 完整部门路径”；同名员工附带联系人 ID，避免选错记录。
4. 点击“预览补人影响”调用预览接口。
5. 预览区展示新增成员、自评任务、互评任务、收到新待办的原成员人数和截止时间。
6. 警告文案明确说明：“补人不会改动已有答卷，但同组原成员会收到新的评价任务。”
7. 管理员点击“确认补充并生成任务”后执行正式接口。

### 5.3 成功与失败反馈

成功后：

- 关闭弹窗。
- 刷新参评人员列表。
- 通知上层刷新关系复核和进度数据。
- 提示实际新增成员数和关系数。

失败时保留管理员当前选择，并显示具体处理方法：

- 批次已截止：关闭补人弹窗并刷新批次状态。
- 成员已被加入：刷新候选列表，要求重新预览。
- 联系人停用或组织归属异常：展示具体员工和异常原因。
- 网络失败：允许使用原选择重新预览，不重复提交正式请求。

## 6. 数据口径

- 任务总数、完成率、应收评价数和后续个人结果均以补人后的实际关系集合计算。
- 已完成员工可能因新增关系再次出现待办状态，这是完整双向互评规则带来的预期变化。
- 已提交答卷保持原 `responseId` 和内容，不重新评分、不失效、不迁移。
- 批次最终锁定和归档沿用现有流程；管理员必须等待新增任务完成或主动登记豁免。

## 7. 安全边界

- 不允许通过补人接口删除或修改既有成员。
- 不允许补充已停用联系人。
- 不允许补充特殊人员；特殊关系仍走现有人工配置流程。
- 不允许在截止、锁定或归档后改变成员和任务范围。
- 不允许客户端传入小组快照、问卷模板或关系类型；这些值由服务端依据批次和通讯录计算。
- 管理员鉴权沿用现有 `/api/admin/eval` 守卫。

## 8. 测试

### 8.1 纯计算与服务测试

- 新成员生成一条自评。
- 新成员与同组原成员生成双向互评。
- 两名新成员同时加入时生成正确的自评和互评。
- 多个共享小组不会重复生成同一有向关系。
- 人工关系占用同一有向人员对时不新增自动关系。
- 不补建与新成员无关的旧缺失关系。

### 8.2 数据安全测试

- 已有答卷的批次可以补人。
- 补人前后的原成员、原关系、`responseId` 和答卷内容完全一致。
- 重复提交同一联系人被拒绝，不产生重复快照或任务。
- 预览后批次截止时，正式执行被拒绝且不写入任何数据。
- 联系人停用、缺少主部门、存在多个主部门时阻止补人。
- 事务中任一步失败时，新增成员、快照、关系和审计全部回滚。

### 8.3 前端验收

- 草稿显示原人员范围入口，已发布未截止显示补人入口，其余状态不显示。
- 候选列表不包含已有成员，同名员工可通过路径和 ID 区分。
- 预览统计与正式执行返回一致。
- 成功后人员、关系复核、进度和员工填写端任务同步更新。
- 失败后选择不丢失，并能按提示重新处理。

## 9. 本地验收步骤

1. 新建并发布一个包含至少两名同组员工的 V2 测试批次。
2. 让其中一名原成员提交至少一份问卷。
3. 从“参评人员”页补充一名同组成员。
4. 验证新成员获得自评和评价原成员的任务。
5. 验证原同组成员获得评价新成员的新增任务。
6. 验证原答卷、原关系和 `responseId` 未变化。
7. 验证补人影响统计、关系复核和总体进度一致。
8. 将批次截止后再次尝试补人，确认操作被拒绝。

## 10. 验收标准

1. 已发布且未截止的 V2 批次可以一次补充多名普通成员。
2. 补入成员按照其当期小组快照完整加入双向互评。
3. 已有关系、人工关系和答卷不被删除或修改。
4. 已有答卷时仍可安全补人，原成员能看到新增待办。
5. 预览明确展示影响范围，正式执行具有后端二次校验和审计记录。
6. 截止、锁定、归档状态无法补人。
