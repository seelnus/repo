# 通讯录与多级组织架构改造设计

**日期**：2026-09-02

**状态**：用户已批准，包含 2026-09-02 补充确认的导入差异确认与钉钉式组织架构界面

**实施范围**：第一阶段仅改造通讯录与组织架构；360 自评/互评关系生成另行设计和实施

## 1. 背景

当前联系人只有一个可自由输入的 `department` 文本字段。联系人编辑、搜索、CSV 导入导出和 360 人员候选均直接读取该字段。当前实现存在以下问题：

1. 部门没有稳定 ID、父子层级、排序和启停状态，改名或手工输入差异会形成多个逻辑部门。
2. 一名员工只能填写一个部门，不能表达主部门、兼任部门和部门内职责。
3. 联系人导入按姓名执行 upsert，同名员工存在误覆盖风险。
4. “属于某部门”和“参加该部门 360 互评”没有分离，无法表达兼任但不参与互评的情况。
5. 如果直接改写现有字段和 360 生成逻辑，会同时影响通讯录、白名单、登录身份匹配和历史环评，发布风险过大。

本次先建立稳定的组织基础数据，并保持现有 360 关系生成逻辑不变。第二阶段验收通讯录数据后，再让新建的 360 批次使用新的多部门模型。

## 2. 已确认的业务规则

1. 组织架构支持公司、中心、部门、项目组等多级节点。
2. 员工只允许归属到末级部门；父级部门用于组织展示、筛选和批量选择。
3. 每名员工必须有且只有一个主部门，可以有多个兼任部门。
4. 主部门默认参加该部门互评；兼任部门默认不参加，可以逐个开启“默认参加该部门互评”。
5. 一般员工与领导使用同一套多部门模型，不通过“领导”标签决定评价范围。
6. 部门内的组织职责按员工与部门的关系保存，例如“负责人、主管、组长、协作”，不同部门可以不同。
7. 通讯录保存长期默认配置；未来创建 360 批次时继承默认值，并允许仅对当期调整。
8. 一名员工进入多个评价小组时，未来仍只生成一条自评；重复的评价人—被评人关系需要去重。该规则属于第二阶段，本阶段只保存默认配置。
9. 暂不接入钉钉开放平台，组织树和人员归属通过本系统手工维护或文件导入。

## 3. 目标与非目标

### 3.1 第一阶段目标

- 建立可维护的多级部门树。
- 支持员工一个主部门和多个兼任部门。
- 支持部门内职责和兼任部门默认互评开关。
- 支持手工创建、编辑、移动、停用部门。
- 支持新的组织架构 Excel 导入预览与应用流程。
- 保留现有联系人 CSV 导入作为兼容入口。
- 保持白名单、企微身份匹配、普通问卷和现有 360 批次可用。
- 为第二阶段提供稳定的部门 ID 和员工—部门关系。

### 3.2 第一阶段非目标

- 不接入钉钉 API、事件订阅或定时同步。
- 不修改现有 360 自动关系生成算法。
- 不让历史批次动态跟随通讯录变化。
- 不实现任意角色条件、权重或方向组成的通用评价规则引擎。
- 不改变当前企微填写登录方式。

## 4. 用户界面设计

### 4.1 通讯录页面布局

原“联系人”入口保留，默认采用参照钉钉通讯录的横向组织架构视图：

- 画布从公司根节点向右展示多级部门，部门节点显示直属人数、包含后代人数和是否还有下级。
- 点击部门节点时，右侧打开部门详情抽屉；抽屉展示部门路径、直属成员、兼任成员和下级部门数量。
- 抽屉内提供搜索成员、添加员工、新增下级、编辑部门、停用部门和查看全部员工入口。
- 成员列表明确标记“主部门”或“兼任”，不把兼任员工重复创建成多个联系人。
- 页面保留“组织架构、员工列表”视图切换；员工列表继续支持按父级部门、主部门、兼任部门和状态筛选。
- 页面顶部提供搜索、导出、导入同步、新增员工和身份冲突入口。
- 大型多级架构支持聚焦当前分支、缩放和重置视图；窄屏改为纵向分支并把部门抽屉放在底部。

页面只使用业务术语“主部门、兼任部门、是否参加该部门互评”，不显示“多对多关系、规则引擎、快照”等技术概念。

### 4.2 部门管理

管理员可以：

- 新建根节点或子部门。
- 修改名称、排序和父部门。
- 移动整棵子树。
- 停用部门及其后代节点。
- 查看直接人数和包含后代的人数。

限制规则：

- 部门编码全局唯一，创建后不可修改，用于导入匹配。手工创建时由系统自动生成，导入时由模板提供。
- 同一父节点下不能存在同名部门；需要恢复旧部门时应重新启用原节点，避免一条路径对应多个 ID。
- 不能把部门移动到自身或自身后代，防止形成循环。
- 只有末级部门可以绑定员工。
- 已绑定员工的末级部门不能直接新增子部门；必须先将员工迁移到新的末级节点。
- 有成员、子部门或历史引用的部门不能物理删除，只能停用。
- 停用部门前展示受影响员工，确认后员工保留原归属但被标记为“部门已停用”，要求管理员后续处理。

### 4.3 联系人编辑

联系人基础信息继续包含姓名、工号、职位、手机号、邮箱和标签。部门配置改成独立表格：

| 字段 | 说明 |
|---|---|
| 归属类型 | 主部门或兼任部门 |
| 部门 | 从启用的末级部门树中选择 |
| 组织职责 | 可选文本，例如负责人、主管、组长、协作 |
| 默认参加该部门互评 | 主部门固定开启；兼任部门默认关闭，可手工开启 |

保存页底部显示业务摘要，例如：

> 张经理默认参加“用户运营部、门店管理部”的双向互评；“线下生态体验部”只作为兼任归属。创建 360 批次时可以临时调整。

联系人保存必须在单个数据库事务中完成基础资料、主部门和全部兼任部门更新。

### 4.4 联系人状态与删除

- 新增 `isActive` 状态，在职联系人为启用，离职或暂不使用的联系人为停用。
- 停用联系人不会出现在新白名单或未来新建 360 批次的默认候选中。
- 停用不影响历史白名单、答卷、评价关系或结果查询。
- 已被白名单、答卷或评价关系引用的联系人禁止物理删除。
- 仅完全没有业务引用的误建联系人允许物理删除，并要求二次确认。

## 5. 数据模型

### 5.1 `OrgDepartment`

新增组织部门表：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Int | 主键 |
| `code` | VarChar(64) | 稳定部门编码，全局唯一，创建后不可修改 |
| `name` | VarChar(200) | 当前节点名称 |
| `parentId` | Int? | 父部门 ID；根节点为空 |
| `sortOrder` | Int | 同级排序 |
| `isActive` | Boolean | 是否启用 |
| `createdAt` / `updatedAt` | DateTime | 创建与更新时间 |

索引和约束：

- `code` 唯一。
- `parentId + name` 唯一，避免同一父节点下重名。
- `parentId` 建索引。
- 删除行为使用 `Restrict`，业务层只允许安全的空节点物理删除。

完整路径由服务层从父链计算，不持久化名称路径，避免部门移动或改名后批量更新冗余路径。

### 5.2 `ContactDepartmentMembership`

新增员工—部门关系表：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Int | 主键 |
| `contactId` | Int | 联系人 ID |
| `departmentId` | Int | 末级部门 ID |
| `isPrimary` | Boolean | 是否为主部门 |
| `defaultEvalEnabled` | Boolean | 是否默认参加该部门互评 |
| `roleName` | VarChar(100)? | 该员工在该部门的职责 |
| `createdAt` / `updatedAt` | DateTime | 创建与更新时间 |

约束：

- `contactId + departmentId` 唯一。
- 一个联系人只能有一条 `isPrimary=true` 的关系，由联系人保存事务和数据库事务锁共同保证。
- 主部门关系的 `defaultEvalEnabled` 必须为 `true`。
- 兼任部门默认值为 `false`。
- 部门必须存在、启用且没有子节点。

### 5.3 扩展 `Contact`

新增：

- `isActive Boolean @default(true)`。
- `memberships ContactDepartmentMembership[]` 关系。

同时调整人员身份约束：

- 移除 `name` 的唯一约束，允许不同员工同名。
- 手机号保存前统一去除空格和常见分隔符，继续作为企微身份和导入的首选匹配键；新增和修改由业务层阻止产生新的重复手机号。
- 工号保持可空；导入时只有在工号全局唯一的情况下才允许作为回退匹配键。
- 现存重复手机号不自动合并或删除，在通讯录和导入预览中标记为身份冲突；全部历史冲突人工处理完成后，再单独增加数据库唯一约束。

现有 `department` 文本字段暂时保留，用作旧页面、导出和现有 360 逻辑的兼容字段：

- 迁移时不改变现有值。
- 通过新页面选择主部门后，将其同步为主部门完整路径，分隔符统一为 `/`。
- 第二阶段 360 全面改用部门 ID 与批次快照后，再单独评估是否移除该字段；本阶段不删除。

## 6. 导入与导出

### 6.1 兼容现有联系人 CSV

原联系人 CSV 入口保留，字段仍为姓名、部门、工号、职位、手机号、邮箱和标签。

改进规则：

- 不再按姓名 upsert。
- 优先按规范化手机号匹配；手机号为空或重复时拒绝该行。
- 手机号无法匹配时，仅在工号非空且全局唯一时允许按工号匹配。
- 姓名仅用于显示和差异提示，不能作为自动覆盖依据。
- `部门` 按 `/` 解析为部门路径；路径不存在时，在预览中提示可创建的节点，不静默创建。
- 应用导入前必须展示新增、更新、未匹配、冲突和跳过统计。

### 6.2 新组织架构 Excel

新增 XLSX 模板，包含三个工作表：

#### `部门`

| 部门编码 | 部门名称 | 父部门编码 | 排序 | 状态 |
|---|---|---|---|---|

#### `员工`

| 姓名 | 手机号 | 工号 | 职位 | 邮箱 | 标签 | 主部门编码 | 状态 |
|---|---|---|---|---|---|---|---|

#### `兼任部门`

| 手机号 | 工号 | 部门编码 | 组织职责 | 默认参加互评 |
|---|---|---|---|---|

同一员工存在多个兼任部门时，在“兼任部门”工作表中占多行。手机号为首选人员匹配键，工号仅作为唯一回退键。

### 6.3 导入流程

1. 上传文件并执行只读解析，生成本次文件哈希和稳定的差异项 ID。
2. 后端完整校验部门树、人员匹配和关系约束，并把结果分为“自动新增、待确认变更、停用候选、冲突、无变化”。
3. 自动新增不要求逐条确认；页面只展示新增员工和新增部门数量，并允许查看只读清单。
4. 待确认变更包括员工资料变化、调岗、主部门变化、兼任部门增减、互评开关变化、部门改名和部门移动。每条必须返回变更前、变更后的字段值。
5. 待确认变更默认全部勾选，管理员可以取消任意一条；取消的记录保持系统原状。
6. 最新全量文件中不存在的启用员工或部门进入“停用候选”，默认勾选；确认后只停用、不物理删除，历史问卷和 360 数据保持不变。
7. 冲突记录不允许勾选，必须展示冲突原因；冲突记录本身不写入，但不阻止其他无冲突且已确认的数据同步。
8. 无变化记录默认折叠，不进入确认数量。
9. 底部主按钮明确展示即将执行的结果，例如“新增 12 条，应用变更 7 条，停用 3 条”。
10. 正式应用必须携带文件哈希和已勾选的差异项 ID；后端重新解析并校验文件，文件或当前数据库状态发生变化时拒绝应用并要求重新预览。
11. 无冲突的数据在单个事务中应用；任何一条已选记录写入失败时整批回滚。

本次先对系统定义的三工作表组织 Excel 实现该机制。钉钉原始导出格式需要拿到实际脱敏样表后增加适配器，不在没有样表的情况下猜测表头和身份字段。

阻断错误包括：

- 部门编码重复或父部门不存在。
- 部门形成循环。
- 员工绑定到非末级部门。
- 一个员工存在多个主部门。
- 主部门未开启默认互评。
- 手机号或工号匹配到多个人。
- 兼任部门与主部门重复。

### 6.4 导出

- 原 `contacts.csv` 继续导出主部门兼容路径，保证现有使用方式可继续。
- 新增“导出组织架构 Excel”，使用与导入一致的三个工作表，可作为备份和下次修改模板。

## 7. 后端接口边界

新增部门接口：

- `GET /api/admin/org/departments/tree`
- `POST /api/admin/org/departments`
- `PUT /api/admin/org/departments/:id`
- `POST /api/admin/org/departments/:id/move`
- `PUT /api/admin/org/departments/:id/status`
- `DELETE /api/admin/org/departments/:id`，仅安全空节点可用

联系人接口调整：

- `GET /api/admin/contacts` 返回主部门、全部部门关系、完整路径和状态。
- `POST /api/admin/contacts` 与 `PUT /api/admin/contacts/:id` 接收 `memberships`，在事务中保存。
- `PUT /api/admin/contacts/:id/status` 单独启停联系人。
- 现有不带 `memberships` 的请求在兼容期继续接受，并只更新基础字段。

导入导出接口：

- `POST /api/admin/org/import/preview`，返回文件哈希、分类统计、字段级前后差异和冲突
- `POST /api/admin/org/import/apply`，接收同一文件、文件哈希和已确认差异项 ID
- 原 `POST /api/admin/org/import?dryRun=true|false` 在兼容期保留
- `GET /api/admin/org/export`
- 现有 `/api/admin/contacts/import` 和 `/api/admin/contacts/export` 保留。

所有新增与修改接口继续受 `AdminAuthGuard` 保护。

## 8. 迁移与兼容策略

### 8.1 数据库迁移

1. 新建组织部门表和员工—部门关系表。
2. 为联系人增加 `isActive`，默认全部启用并移除姓名唯一约束；保留现存重复手机号并由业务层禁止新增冲突。
3. 遍历现有非空 `Contact.department`：
   - 按 `/` 拆分路径并创建或复用组织节点。
   - 为联系人创建主部门关系。
   - 保持原 `Contact.department` 文本完全不变。
4. 部门为空的联系人保留为“未归属”，不伪造部门；通讯录页面提供专门筛选和补录入口。
5. 迁移只新增表、字段和关系，不删除原数据。

### 8.2 对现有业务的影响

- 企微登录仍按联系人手机号等现有条件匹配，不改变。
- 普通问卷、白名单和答卷读取联系人 ID，不改变。
- 现有 360 批次、关系和答卷不改写。
- 第一阶段的 360 人员候选和旧自动生成仍读取兼容 `Contact.department`。
- 新页面修改主部门时同步兼容路径，因此新的联系人仍能被当前 360 逻辑识别。
- 部门改名或移动会改变相关联系人的兼容路径；保存前显示受影响人数，并提示尚未生成关系的旧版草稿批次可能需要重新确认范围。

## 9. 错误处理与安全边界

- 部门移动、联系人保存和正式导入均使用数据库事务。
- 部门树写操作执行循环检查、父节点状态检查和末级节点检查。
- 删除联系人前检查白名单成员、答卷、评价关系和批次参与人引用。
- 所有批量导入先 preview，不允许跳过预览直接应用。
- 应用阶段校验文件哈希、差异项 ID 和数据库基线，防止预览后数据变化导致错误覆盖。
- 导入错误返回工作表、行号、字段名和可读原因。
- 单行错误不会被静默跳过；正式应用存在阻断错误时整批回滚。
- 本地实现和验证完成前不执行生产数据库迁移或发布。

- 文件哈希或数据库基线变化后，旧预览不能继续应用。
- 冲突记录不写入，其他已确认的安全记录可以正常同步。
- 现有联系人、白名单、企微登录和普通问卷接口回归。
- 现有 360 列表、历史关系和答卷查询回归。

### 10.3 前端验收

- 横向组织架构可按多级分支展开、筛选、新建、改名、移动和停用。
- 点击部门节点后，右侧抽屉准确展示直属成员、兼任成员、下级数量和部门操作。
- 联系人可以选择一个主部门和多个兼任部门。
- 业务摘要准确展示默认参加互评的部门。
- 父级部门筛选包含所有后代人员。
- 未归属、部门停用、联系人停用状态清晰可见。
- 导入预览按分类显示统计，变更默认全选并能逐条取消。
- 变更列表直接显示关键变化，展开后能查看完整字段级变更前后值。
- 冲突能定位到具体工作表、行号、员工或部门及冲突原因。
- 窄屏下组织分支、底部部门详情和导入确认仍可操作。

## 11. 第一阶段验收标准

1. 现有联系人全部可见，姓名、手机号、工号和原部门数据不丢失。
2. 可创建截图所示的多级组织结构。
3. 一名员工可保存一个主部门和至少两个兼任部门。
4. 主部门固定参加互评，兼任部门可以分别开启或关闭默认互评。
5. 同一员工在不同部门可以保存不同组织职责。
6. 手工编辑、兼容 CSV 和新组织 Excel 三种维护方式均可用。
7. 同名员工不会因导入被错误覆盖。
8. 组织导入必须经过差异预览，错误行不会部分写入。
9. 普通问卷、白名单、企微登录和现有 360 历史数据回归通过。
10. 第一阶段上线后，现有 360 自动关系数量和生成规则不发生变化。
11. 新增记录无需确认；所有更新、调岗、兼任调整和停用候选均经过字段级差异预览与人工确认。
12. 组织架构默认使用钉钉式横向画布，部门成员通过右侧抽屉查看和维护。

## 12. 第二阶段接口约定

第一阶段只为未来 360 提供以下稳定输入，不在本次实现中消费：

- 部门稳定 ID 与父子结构。
- 员工全部末级部门归属。
- 每条归属的 `isPrimary`、`defaultEvalEnabled` 和 `roleName`。
- 联系人启停状态。

第二阶段另行设计：批次人员与多小组快照、当期覆盖开关、跨组关系生成、关系去重、自评唯一性、关系预览和发布前异常检查。
